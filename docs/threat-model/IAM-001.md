# IAM-001 — Compromised ECS Workload Identity

## 1. Threat Summary

A fictional AI research assistant is represented as an Amazon ECS task with an assigned IAM task role.

An attacker who compromises the application may be able to use the workload's temporary AWS credentials to perform actions authorized to that role.

The assessment examines whether excessive S3 permissions permit modeled access to restricted research datasets.

The ECS application and AWS resources are architectural representations. Policy artifacts and selected authorization behaviors are implemented and tested offline.

## 2. Protected Assets

- Approved synthetic research documents.
- Restricted synthetic research datasets.
- ECS workload identity and temporary credentials.
- IAM identity and resource policies.
- Security audit records.

## 3. Threat Actor and Entry Point

**Threat actor:** External attacker with execution capability inside the fictional application workload.

**Entry point:** Compromised ECS application process.

**Assumption:** The attacker can attempt AWS API operations using the permissions available to the ECS task role.

The assessment does not demonstrate exploitation of ECS, credential extraction, or live AWS access.

## 4. Trust Boundary

**TB-03 — Workload Identity to Data Resources**

The application identity must not access resources beyond its explicitly authorized scope.

## 5. Attack Path

1. The attacker gains execution capability within the application workload.
2. The attacker uses the workload's available AWS identity permissions.
3. The attacker requests an object from a restricted S3 dataset.
4. An excessively broad IAM policy may permit the request.
5. Unauthorized data access occurs if all applicable authorization controls allow it.

This is a modeled attack path, not an executed compromise.

## 6. Security Weakness

The baseline identity policy permits `s3:GetObject` and `s3:ListBucket` against all resources.

This resource scope exceeds the application's intended need to read and list approved research data.

An IAM identity policy alone does not determine every AWS authorization outcome. Explicit denies, resource policies, and applicable organizational controls must also be considered.

## 7. Security Controls and Implementation Status

### Implemented in the Offline Lab

- A baseline identity policy demonstrates excessive S3 resource permissions.
- A hardened identity policy restricts `s3:GetObject` to objects in the approved research bucket.
- The hardened policy restricts `s3:ListBucket` to the approved research bucket.
- Automated tests compare selected permitted and prohibited requests under both policies.

Policies:

- [Baseline policy](../../policies/iam-001-baseline.json)
- [Hardened policy](../../policies/iam-001-hardened.json)

### Architectural Intentions and Proposed Controls

- Use temporary workload credentials.
- Separate application and administrative identities.
- Prevent unnecessary administrative and role-assumption capabilities.
- Monitor unexpected S3 access attempts.

These runtime and monitoring controls are not deployed or validated in this scenario. Role-assumption policy restrictions are assessed separately in IAM-002.

## 8. Validation and Evidence

Five automated regression tests pass using the project's limited offline identity-policy evaluator.

The tests verify that:

- The baseline permits reading an approved research object.
- The baseline permits reading a restricted research object.
- The hardened policy preserves approved object access.
- The hardened policy implicitly denies restricted object access.
- The hardened policy implicitly denies listing an unrelated bucket.

## 9. Residual Risks and Limitations

- A compromised workload may still access and misuse resources legitimately permitted to its role.
- Resource-scoped IAM policies do not prevent misuse of authorized data.
- The evaluator implements a limited subset of IAM identity-policy authorization semantics.
- Matching conditional statements and statements containing `NotAction` or `NotResource` are flagged as `UNSUPPORTED` rather than treated as definitive authorization decisions.
- `UNSUPPORTED` indicates an indeterminate offline result, not an AWS access-denied decision.
- IAM conditions, resource policies, service control policies, permissions boundaries, session policies, and other applicable mechanisms are not comprehensively modeled.
- Some unsupported policy constructs may remain unrecognized.
- The evaluator is not suitable for production authorization decisions.
- CloudTrail logging and detection remain proposed.
- No live AWS access or cloud-side enforcement was tested.

## 10. Implementation Status

**Status:** Threat modeled; baseline and hardened policy artifacts implemented; five offline regression tests passing.

No live AWS compromise, credential extraction, or unauthorized S3 access has been performed.

Production effectiveness is not established.
