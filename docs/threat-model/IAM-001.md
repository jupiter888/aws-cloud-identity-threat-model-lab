# IAM-001 — Compromised ECS Workload Identity

## 1. Threat Summary

A fictional AI research assistant runs as an Amazon ECS task with an assigned IAM task role.

An attacker who compromises the application may be able to use the workload's temporary AWS credentials to perform actions authorized to that role.

The assessment examines whether excessive S3 permissions allow unauthorized access to restricted research datasets.

## 2. Protected Assets

- Approved synthetic research documents.
- Restricted synthetic research datasets.
- ECS workload identity and temporary credentials.
- IAM identity and resource policies.
- Security audit records.

## 3. Threat Actor and Entry Point

**Threat actor:** External attacker with execution capability inside the fictional application workload.

**Entry point:** Compromised ECS application process.

**Assumption:** The attacker can invoke AWS APIs using the permissions available to the ECS task role.

The initial assessment does not attempt to demonstrate exploitation of ECS itself.

## 4. Trust Boundary

**TB-03 — Workload Identity to Data Resources**

The application identity must not access resources beyond its explicitly authorized scope.

## 5. Attack Path

1. The attacker gains execution capability within the application workload.
2. The attacker uses the workload's available AWS identity permissions.
3. The attacker requests an object from a restricted S3 dataset.
4. An excessively broad IAM policy may permit the request.
5. Unauthorized data access occurs if all applicable authorization controls allow it.

## 6. Security Weakness

An identity policy permitting `s3:GetObject` against an unnecessarily broad resource scope can expose datasets unrelated to the application's intended function.

An IAM identity policy alone does not determine every authorization outcome. Explicit denies, resource policies, and applicable organizational controls must also be considered.

## 7. Proposed Mitigations

- Restrict `s3:GetObject` to approved object ARNs.
- Separate approved and restricted dataset permissions.
- Prevent unnecessary administrative and role-assumption capabilities.
- Use short-lived workload credentials.
- Monitor unexpected S3 access attempts.
- Validate both allowed and denied authorization cases.

## 8. Validation Plan

Create two synthetic IAM policies:

**Baseline:** Overprivileged S3 read permissions.

**Hardened:** Resource-scoped permissions for approved research objects.

Test both policies against representative permitted and prohibited S3 requests.

Tests will model selected authorization conditions rather than claim full equivalence with AWS IAM evaluation.

## 9. Residual Risks

- A compromised workload may still access resources legitimately permitted to its role.
- Resource-scoped IAM policies do not prevent misuse of authorized data.
- Offline policy tests do not reproduce every AWS authorization mechanism.
- Logging supports investigation but does not automatically prevent unauthorized access.

## 10. Implementation Status

**Status:** Threat modeled; validation pending.

No live AWS compromise, credential extraction, or unauthorized S3 access has been performed.
