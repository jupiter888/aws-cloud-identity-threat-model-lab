# IAM-002 — Unauthorized STS Role Assumption

## 1. Threat Summary

A fictional AI research assistant is represented as an Amazon ECS task using an assigned IAM task role.

An attacker who compromises the workload attempts to assume a separate, more privileged research administration role using AWS Security Token Service (STS).

The ECS application, AWS roles, and STS operations are architectural representations. Caller policies, trust policies, and selected authorization behaviors are implemented and tested offline.

## 2. Protected Assets

- Privileged research administration role.
- Restricted synthetic research datasets.
- IAM role trust relationships.
- Temporary STS credentials.

## 3. Attacker Starting Position

The attacker is assumed to have obtained code execution within the fictional ECS application workload.

The attacker can attempt AWS API operations using the workload's available IAM identity.

The attacker does not initially possess administrator credentials.

Application exploitation and credential extraction are not demonstrated.

## 4. Attack Path

1. Compromise the ECS application workload.
2. Identify a privileged IAM role.
3. Invoke `sts:AssumeRole` targeting that role.
4. Exploit permissive caller permissions and target-role trust.
5. Obtain temporary credentials if all applicable authorization requirements are satisfied.
6. Attempt access to restricted research resources using the assumed role.

The offline lab evaluates selected authorization checks for step 4. It does not issue credentials or perform downstream resource access.

## 5. Trust Boundary

**TB-04 — Workload Identity to Privileged Role Assumption**

The offline model requires both the caller-policy check and the target-role trust check to allow the request.

This simplified requirement does not reproduce all AWS role-assumption authorization semantics, including same-account variations.

## 6. Baseline Weakness

The baseline caller policy permits the application workload to invoke `sts:AssumeRole` against the fictional ResearchAdmin role.

The baseline ResearchAdmin trust policy permits the application role.

Together, these configurations produce an `ALLOW` result in the lab's simplified role-assumption model.

## 7. Security Controls and Implementation Status

### Implemented in the Offline Lab

**IAM-002-C1 — Caller Permission Restriction**

The hardened caller policy grants no `sts:AssumeRole` permission to the application workload.

This is a removal of permission in the modeled policy, not an explicit deny or proof that no other policy could grant access.

**IAM-002-C2 — Target-Role Trust Restriction**

The hardened ResearchAdmin trust policy permits the dedicated SecurityAdmin role instead of the application role.

The two controls are tested independently and together.

- Monitor role-assumption events using CloudTrail.

Monitoring, alerting, conditions, and organizational guardrails are not implemented or validated in this lab.

## 8. Validation and Evidence

Five automated regression tests pass using the project's limited offline IAM and STS evaluators.

The tests verify that:

- Baseline caller and baseline trust policies permit the application's modeled role-assumption request.
- The hardened caller policy blocks that modeled request when paired with baseline trust.
- The hardened trust policy blocks that modeled request when paired with the baseline caller policy.
- Combining both hardened controls blocks that modeled request.
- The hardened trust policy recognizes SecurityAdmin as an authorized principal.

Recognition of SecurityAdmin by the trust-policy evaluator does not independently establish successful role assumption by that principal.

## 9. Scope and Limitations

All resources and identities are fictional.

No AWS accounts, real credentials, or live STS operations are used.

The offline STS evaluator models selected caller-policy and target-role trust checks, not the complete AWS role-assumption authorization process.

The trust-policy evaluator does not comprehensively detect or evaluate IAM conditions, principal variations, or other advanced trust-policy syntax.

Same-account authorization semantics, session policies, permissions boundaries, and organizational controls are not comprehensively modeled.

Offline `ALLOW` and `IMPLICIT_DENY` results describe the modeled checks only. They do not establish actual AWS authorization, and unsupported constructs must not be interpreted as reliably evaluated.

Other applicable policies could affect effective permissions. Compromise of an authorized administrator also remains possible.

CloudTrail detection and alerting have not been implemented.

**Implementation status:** Threat modeled; caller and trust policy mitigations implemented; five offline regression tests passing.

Production effectiveness is not established.
